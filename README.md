# NOVA Engine

Модульная CMS и платформа интернет-магазинов и маркетплейсов на JavaScript. Текущая версия — **0.21**. Ниже после инструкции запуска приведена история возможностей по версиям.

## Установка на новый VDS

[Установка одной командой](docs/INSTALL.md): Ubuntu 22.04/24.04 или Debian 12/13, Docker, PostgreSQL, HTTPS и админка по `/admin/`. Требуются свободные порты 80/443 и заранее настроенный домен. Установщик предназначен для отдельного сервера и не заменяет существующую установку с aaPanel.

[Установка на хостинг, 1Gb.ru и VDS с панелью](docs/HOSTING.md) · [Системные требования и проверка тарифа](docs/REQUIREMENTS.md).

## Состав
- `apps/storefront` — Vue 3 витрина, порт 5173
- `apps/admin` — Vue 3 административная панель, порт 5174
- `apps/api` — Fastify REST API, порт 3001
- PostgreSQL 17 — каталог, контент, заказы и покупатели

## Первый запуск на Windows
Понадобятся Node.js 22+, npm и Docker Desktop (с запущенным Docker Engine).

1. `git clone https://github.com/maxx52/nova-engine.git`
2. `cd nova-engine`
3. `copy .env.example .env` (в PowerShell: `Copy-Item .env.example .env`)
4. В `.env` **обязательно замените** `ADMIN_API_KEY` на собственный случайный секрет длиной не менее 16 символов. Учётные данные базы в примере предназначены только для локальной разработки.
5. `docker compose up -d`
6. `npm ci`
7. `npm run dev:all`

Откройте:
- Витрина: http://localhost:5173
- Администратор: http://localhost:5174
- Проверка API: http://localhost:3001/health

При первом входе в NOVA Admin создайте администратора с помощью `ADMIN_API_KEY`. Затем вход выполняется по логину и паролю; сессия хранится в HttpOnly cookie. Ключ первоначальной настройки не является API-ключом для повседневной работы.

Для остановки: `Ctrl+C` в терминале разработки и `docker compose down` для базы. Команда `docker compose down -v` **удалит данные PostgreSQL**.

## Важные ограничения
- Перед публичным размещением примените production-конфигурацию из `SECURITY.md`: HTTPS, собственные секреты, ограниченная роль БД, закрытые внутренние порты и резервное копирование.
- Товары сохраняются в PostgreSQL. Витрина читает их при загрузке страницы.
- Гостевое оформление заказов доступно. Оплату можно подключить готовой ссылкой или публичным кодом виджета; поступления подтверждаются вручную. Автоматический платёжный API, расчёт доставки, личные кабинеты покупателей и уведомления о заказах не подключены. Формы обратной связи поддерживают email и Telegram.
- При первом запуске с пустой таблицей добавляются шесть демонстрационных товаров.
- Для production нужны миграции БД, безопасное хранение секретов и резервное копирование.

## NOVA 0.5 — фотогалерея и страница товара
- Товар может содержать до 12 загруженных изображений, с выбором главного фото в редакторе NOVA Admin.
- Старое поле `image_url` сохраняется; существующие фотографии автоматически переносятся в массив `images` при запуске API.

- Фотографии находятся в локальной папке `uploads/`, **включайте её в резервное копирование** вместе с PostgreSQL.
- Обновление схемы выполняется автоматически. Перед запуском новой версии рекомендуется резервная копия БД.
- Пока это локальный прототип; варианты, характеристики, SEO и полноценная авторизация впереди.

## NOVA 0.6 — характеристики и варианты
- В редакторе товаров NOVA Admin доступны вкладки «Основное», «Фотографии», «Характеристики», «Варианты».
- Характеристики — произвольные пары «название / значение», до 50 на товар.
- Варианты — до 100 записей на товар: название (например, «Красный / M»), артикул, цена и остаток. На витрине покупатель выбирает вариант перед добавлением в демонстрационную корзину.
- Два новых JSONB-поля `attributes` и `variants` добавляются к существующей таблице без сброса данных.
- Важно: это **прототип**, без атомарного резервирования остатков, оформления заказов и авторизации покупателей. Не предназначено для реальных продаж.

## NOVA 0.7 — категории и фильтры
- NOVA Admin: создание и редактирование категорий, родительские категории, шаблоны характеристик (через запятую).
- В редакторе товара: кнопка «Применить шаблон категории» добавляет незаполненные характеристики, которые необходимо заполнить перед сохранением.
- Витрина: поиск по названию, артикулу, описанию и характеристикам; фильтр по значению характеристики; выбор родительской категории охватывает товары из дочерних категорий.
- Ограничения: категории пока связаны с товарами по имени, не по внешнему ключу. Переименование категории само по себе не переносит товары. Фильтрация пока выполняется в браузере — для больших каталогов нужна серверная пагинация и индексы. Вложенность отображается упрощённо.

## NOVA 0.8 — страницы сайта

В NOVA Admin доступен раздел **Страницы**: заголовок, уникальный адрес
(например `about`), обычный текст и статус публикации. Страница открывается
на витрине по `/about`. Переносы строк сохраняются, HTML отображается как текст.
Черновики доступны только через защищённый административный API.
Для загрузки списка страниц сначала введите ключ API в админке.

Таблица `pages` создаётся автоматически при запуске API; существующий каталог
не изменяется. Конструктор секций, меню сайта, блог и переключение модулей
пока не реализованы. Магазин остаётся демонстрационной главной страницей.
При размещении на сервере настройте SPA fallback на `index.html` для адресов страниц,
исключив `/api` и `/uploads`. Внешний адрес витрины для ссылок админки можно задать
переменной `VITE_SITE_URL` (локально используется `http://localhost:5173`).

Проверка API страниц: `node --test apps/api/test/pages.test.js`.

## NOVA 0.9 — секции страниц

В редакторе страницы можно добавлять до 50 секций и менять порядок стрелками:
- **Обложка** — заголовок, текст, фоновая фотография и ссылка-кнопка.
- **Текст** — заголовок и обычный текст с сохранением переносов.
- **Изображение** — загруженная фотография, описание для доступности и подпись.

Изображения загружаются через существующий защищённый API: JPG, PNG, WebP до 5 МБ.
Кнопка принимает внутренний путь (`/about`) или HTTP(S) адрес.
Все изменения секций применяются после сохранения страницы. Удаление секции
или изображения из страницы не удаляет файл из `uploads`.
Секции хранятся в `pages.sections` (JSONB), колонка добавляется автоматически
при старте API. Старый текст сохраняется и выводится перед секциями.
Публикация и черновики работают для всей страницы.

Проверки: `npm run build`, `node --test apps/api/test/pages.test.js`.
HTTP-тесты используют Fastify inject и подменённое хранилище; это не проверка
реального PostgreSQL. Назначение страницы главной и визуальный предпросмотр
в админке пока не реализованы.

## NOVA 0.10 — настройки сайта и меню

В разделе **Настройки** доступны название сайта, загрузка логотипа,
выбор опубликованной страницы как главной, меню (до 20 ссылок с изменением
порядка) и переключатель магазина. Изменения применяются после сохранения;
открытый сайт нужно обновить.

Главная выбранная страница открывается на `/` и сохраняет собственный адрес.
При включённом магазине демонстрационный каталог доступен на `/catalog`.
Без выбранной главной на `/` открывается магазин, а при отключённом магазине —
простая стартовая страница с названием сайта. Если главная стала черновиком
или была удалена, используется тот же запасной вариант.

При отключении магазина скрываются его пункты в админке, корзина и ссылки
меню на `/catalog` и `/product/...`. Публичные запросы товаров и категорий
возвращают 404; административные запросы с корректным ключом остаются доступны.
Товары, категории и изображения не удаляются. Это переключение функций
существующего приложения; загрузчик внешних модулей пока не реализован.

Настройки сохраняются в таблице `site_settings`, которая создаётся при старте
API с прежним магазином в качестве значения по умолчанию. Установка обновления:
`git pull origin main`, `npm install`, `npm run dev:all`.

Проверки: `npm run build` и `node --test apps/api/test/*.test.js`.
HTTP-тесты используют подменённое хранилище; настоящий PostgreSQL и браузер
в этой среде не проверены.

## NOVA 0.11 — блог

1. Введите ключ администратора, откройте **Настройки** и включите блог.
2. Сохраните настройки — в админке появится раздел **Блог**.
3. Создайте статью: заголовок, адрес, краткое описание, текст, рубрика,
   теги через запятую и обложка (JPG/PNG/WebP до 5 МБ).
4. Включите «Опубликована» и сохраните. Статья доступна по `/blog/адрес`.
5. Добавьте в настройках меню ссылку `/blog` для посетителей.

На `/blog` доступны фильтры по рубрике и тегу и постраничная выдача по 12 статей.
Рубрики и теги задаются в статьях; отдельного справочника рубрик пока нет.
Текст выводится с сохранением абзацев и экранированием HTML. Богатый текстовый
редактор, авторы и публикация по расписанию пока не реализованы.
Дата публикации устанавливается при первой публикации и сохраняется при
редактировании и повторной публикации.

Блог по умолчанию выключен. Отключение скрывает пункт админки, внутренние
ссылки меню `/blog` и закрывает публичный API; статьи сохраняются и остаются
доступны через административный API с ключом. Магазин переключается независимо.
Таблица `posts`, индекс публикаций и `site_settings.blog_enabled` создаются
при запуске API без удаления существующих данных. Адрес `/blog` зарезервирован.

Проверки: `npm run build`, `node --test apps/api/test/*.test.js`.
HTTP-тесты используют подменённое хранилище. Проверка с настоящим PostgreSQL
и в браузере в этой среде не выполнена.

## NOVA 0.12 — вход администратора

После обновления откройте админку. При первом запуске появится форма создания
администратора: введите текущий `ADMIN_API_KEY` из `.env`, выберите логин
(3–64 латинских символа, цифры, `_`, `-`, `.`) и пароль от 12 до 256 символов.
В дальнейшем требуется только логин и пароль. Ключ остаётся параметром
первоначальной настройки, но больше не принимается как авторизация API.
Повторное создание администратора закрывается после первого успешного создания.

В верхней панели доступны **Сменить пароль** и **Выйти**. Смена пароля требует
текущий пароль и завершает все сессии. Сессия действует 8 часов, переживает
обновление страницы и перезапуск API; истёкшие сессии удаляются при входе.
Пароли хранятся как scrypt-хеши с индивидуальной случайной солью. В PostgreSQL
хранятся хеши токенов сессий, браузер получает HttpOnly-cookie с SameSite=Strict.
Изменяющие запросы требуют CSRF-токен и заголовок `X-Nova-Request: 1`.
Лимит — 10 попыток входа, создания администратора или смены пароля с одного IP
за 15 минут. Лимит хранится в памяти одного процесса и сбрасывается при его перезапуске.

Для локального запуска ничего менять в существующем `.env` не требуется.
При размещении задайте `ADMIN_ORIGINS` точными адресами админки через запятую,
например `https://admin.example.com`, включите HTTPS и `SESSION_SECURE=true`.
При `NODE_ENV=production` Secure-cookie включается автоматически.
Сохраняйте проксирование `/api` с домена админки на API — cookie привязана к этому
домену и пути `/api`. Старые скрипты с `X-Admin-Key` нужно перевести на сессии.

Таблицы `admin_accounts` и `admin_sessions` создаются автоматически, существующее
содержимое сайта не меняется. Пока поддерживается один администратор; роли,
приглашения и восстановление забытого пароля ещё не реализованы.

Проверки: `node --test apps/api/test/*.test.js`, `npm run build`.
Дополнительно SQL миграций и полный цикл входа/смены пароля проверены через
PGlite (встроенный PostgreSQL-движок); это не запуск Docker/PostgreSQL на Windows.

Проверка в Chromium также пройдена: первоначальная настройка, вход/выход,
смена пароля, восстановление сессии при обновлении страницы, защищённое
сохранение страницы через Vite proxy и Fastify с базой PGlite. Проверен
мобильный экран входа. Это не проверка запуска в пользовательском Windows-окружении.

## NOVA 0.13 — медиатека

Раздел **Медиатека** доступен после входа независимо от включения магазина и блога.
В нём можно загружать изображения, искать по имени или адресу файла и просматривать
использование в содержимом. Выдача — по 24 файла. JPG/PNG/WebP до 5 МБ.

В редакторах страниц (обложка и изображение), статей, товаров и в настройках
логотипа появилась кнопка **Выбрать из медиатеки**. Выбор подставляет изображение
в форму; затем нужно сохранить соответствующую страницу, статью, товар или настройки.
Выбор существующего файла не создаёт копию. Для товара сохраняется лимит 12 фото.

При первом запуске обновления существующие файлы из `uploads` автоматически
попадут в медиатеку; для старых файлов исходные имена недоступны, поэтому используется
имя на диске. Новые загрузки сохраняют исходное имя в таблице `media_files`.
Делайте резервную копию PostgreSQL вместе с папкой `uploads`.

Удаление блокируется при использовании в галерее/главном фото товара, обложке
статьи, изображениях секций, логотипе, ссылках кнопок секций или меню на файл.
Учитываются черновики и отключённые разделы. Несохранённые изменения в редакторе
ещё не считаются использованием. База проверяет ссылки при сохранении — удалённый
в другой вкладке файл нельзя вернуть через устаревшую форму. Ссылки HTTP(S) с тем
же путём `/uploads/...` также консервативно считаются использованием.

Удалённый файл перестаёт выдаваться сервером и убирается с диска. Если физическая
очистка временно не удалась, она повторяется при следующем запуске; в базе остаётся
служебная отметка удаления. Автоматического удаления неиспользуемых файлов нет.

Проверены обе сборки, 13 автоматических тестов и SQL-триггеры на PGlite:
импорт старых файлов, использование во всех модулях, удаление и защита устаревших
ссылок. В Chromium проверен выбор изображения с сохранением страницы, запрет
удаления используемого файла и удаление после освобождения. Проверка запуска
на Windows с Docker остаётся на пользовательском окружении.

## NOVA 0.14 — защита

Проведена проверка кода и усилены вход, сессии, загрузка изображений,
HTTP-политики и ограничения ресурсов. Подробности, результаты тестов и условия
размещения — в [SECURITY.md](SECURITY.md).

Для локального обновления: остановите приложение, выполните `git pull origin main`,
`npm ci`, `npm run dev:all`. Docker/PostgreSQL должен работать. Локальную `.env`
не заменяйте — текущие данные входа и содержимое сохраняются.

В верхней панели появилась кнопка **Выйти везде**. Сессия теперь истекает после
30 минут без обращений к API, максимум — 8 часов. Новые фотографии проверяются
декодированием и сохраняются в WebP без метаданных. Ограничения: 5 МБ, до 20 Мп
и 10 000 px по стороне, без анимации. Старые изображения остаются на месте.

Проверки: `npm test`, `npm run build`, `npm audit --audit-level=moderate`.
Серверы разработки слушают 127.0.0.1; для размещения нужны готовая сборка,
HTTPS и отдельные настройки сервера. Nginx-шаблон в `deploy/` не был установлен
на пользовательский VDS автоматически.


## NOVA 0.15 — оформление и редактор кода

В админке появился раздел **Оформление и код**: тексты первого экрана, преимуществ, каталога, корзины и блога; подписи шапки/подвала; цвета, шрифт, ширина и скругления; изображение и ссылка главной кнопки; видимость и порядок блоков. Название, меню и логотип остаются в «Настройках», содержимое — в товарах, страницах и блоге.

Редактор содержит `index.html`, `style.css`, `script.js` и `site.css`. В нём есть номера строк, поиск, Tab/Shift+Tab, Ctrl+S, запуск предпросмотра и выбор ширины. `site.css` применяется к нативному сайту; HTML/CSS/JS создают собственную главную или блок перед подвалом. Отдельные страницы также поддерживают секцию «HTML / CSS / JavaScript».

Оформление сохраняется в PostgreSQL как черновик. Нажатие «Опубликовать» обновляет публичную версию. История хранит последние 30 состояний до сохранения/публикации; восстановление сначала загружает версию в редактор. Сохранения защищены от перезаписи из другой вкладки. При первом обновлении устанавливаются стандартные значения, существующие страницы и товары сохраняются.

Публичные данные доступны коду как `window.NOVA.settings` и `window.NOVA.products`; в предпросмотре используются демонстрационные данные. Никакие пароли, сессии или ключи в блок не передаются. Внутренние ссылки в блоках могут открывать публичные страницы сайта. Свой JS работает в sandbox iframe без доступа к родительскому DOM и cookie. Fetch/XHR запрещены политикой CSP. Это клиентский редактор оформления; файлы Node.js и секреты сервера не редактируются.

### Обновление reverse proxy

Для кода нужен отдельный точный маршрут `/api/code-frame`, сохраняющий CSP с nonce от API. В обоих nginx server-блоках добавьте:

```nginx
location = /api/code-frame {
    include /srv/nova/deploy/code-frame-proxy.conf;
}
```

Укажите в новом snippet фактический локальный порт API. Не включайте в этот location общий `api-proxy.conf`, который скрывает заголовки iframe. Полный пример обновлён в `deploy/nginx.conf.example`. На одном поддомене админку собирайте с `npm run build -w @nova/admin -- --base=/admin/`; ссылка на публичные страницы в production по умолчанию использует текущий домен, либо `VITE_SITE_URL`.

Путь `/uploads/` в nginx использует `deploy/public-media-proxy.conf`: он сохраняет CORP cross-origin и защитные заголовки изображений от API. Это необходимо для фотографий в изолированных блоках кода.

Режим «Полная тема» заменяет содержимое всех публичных маршрутов своим HTML/CSS/JS; видимость нативной шапки и подвала задаётся отдельно. `NOVA.route.path` содержит адрес текущей страницы. Для динамического содержимого используйте `await NOVA.request('/api/products')`, `/api/products/ID`, `/api/categories`, `/api/pages`, `/api/pages/slug`, `/api/blog`, `/api/blog/slug`. Родитель выполняет только GET по этому списку, без cookie; административные и auth-endpoint запрещены. На блок допускается до 100 запросов и 3 одновременных. В предпросмотре мост отключён.


## NOVA 0.16 — заказы и покупатели

Корзина оформляет гостевой заказ: имя, телефон, необязательный email, самовывоз/доставка, адрес и комментарий. В ответе — номер и сумма товаров, без персональных данных. Оплата и стоимость доставки согласуются менеджером отдельно; деньги на сайте не списываются. Все новые подписи формы доступны в «Оформление и код → Тексты».

«Заказы»: поиск по номеру/контактам, фильтр статуса, пагинация, состав с сохранёнными ценами, контакты на момент покупки, внутренние заметки и история обработки. Статусы: новый → подтверждён → в работе → передан в доставку → выполнен; из нового, подтверждённого или находящегося в работе заказ можно отменить. Из «В работе» доступно выполнение без доставки (самовывоз). Завершённые и отменённые заказы не открываются повторно.

«Покупатели»: автоматическое создание карточки по нормализованному телефону, поиск, контакты, внутренняя заметка и история заказов. Это контактные карточки, не проверенные аккаунты: владение телефоном не подтверждается. Редактирование карточки не меняет исторические данные в заказах и не перезаписывается очередным гостевым оформлением.

При оформлении сервер сам читает опубликованные товары, цены, варианты и остатки, затем в одной транзакции уменьшает доступное количество. Нулевой остаток запрещает покупку, в том числе для товара без SKU. Для вариантов учитывается их собственный остаток. Не забудьте задать остатки тестовым товарам через админку: начальные демонстрационные товары имеют 0. Денежные суммы заказов хранятся в целых копейках.

Отмена один раз возвращает остатки существующих товаров и вариантов. Если товар удалён, вариант переименован/удалён либо товар переведён на варианты, история отмены содержит предупреждение о ручной сверке склада; исторический состав заказа сохраняется. Автоматического истечения новых заказов нет: непроверенные заявки нужно отменять вручную. Возвраты после отгрузки/выполнения пока не реализованы.

Публичный `POST /api/orders` требует `x-nova-checkout: 1`, JSON и UUID v4 `request_id`; контакты и позиции валидируются. Повтор с тем же UUID и составом возвращает ту же квитанцию, не списывая остаток снова; изменённый состав с прежним UUID отклоняется. После неопределённого сетевого результата форма предлагает повторить проверку с тем же ключом и фиксирует отправленный состав. Публичного чтения контактов/состава по номеру заказа нет. Списки, детали, статусы и контакты доступны только через административные маршруты с сессией и CSRF для изменений.

Товар теперь возвращает строку `revision`. `PUT /api/products/:id` требует её и возвращает 409 при устаревшей версии — это защищает остатки от перезаписи открытым до покупки редактором. Админка передаёт версию автоматически. Схема добавляется при запуске API; существующие товары и содержимое сайта сохраняются. Новая зависимость PGlite используется только в тестах для проверки настоящего PostgreSQL SQL без отдельного сервера: `npm test`.


## NOVA 0.17 — собственная аналитика

Раздел **Аналитика** работает для магазина, блога, обычных страниц и полной HTML-темы. Показывает посетителей (идентификаторы браузеров), сессии, просмотры, график и таблицу по дням, до 30 популярных адресов, до 20 источников, устройства и браузеры. Предустановлены периоды «Сегодня», 7 и 30 дней; произвольный диапазон — до 90 дней. Есть CSV с агрегатами, днями, страницами и источниками (UTF-8 BOM, разделитель `;`).

События стандартной корзины: добавление товара и начало оформления. Для каждого шага считается число сессий с действием; это не строгая последовательная воронка. Конверсия — доля сессий с просмотром страницы и связанным неотменённым заказом в выбранном периоде. Повторная отправка заказа не создаёт новую конверсию. Заказы без работающего сборщика остаются в общей статистике заказов, но не в конверсии посещений. Произвольный JS собственной темы автоматически получает учёт открытий страниц; действия нестандартной корзины/формы не подменяются событиями стандартной корзины.

Показатели заказов берутся из PostgreSQL независимо от посещений: число оформлений, отмены, выполненные заказы, их сумма товаров без доставки и средний заказ без отмен. Период применяется к **дате оформления**, статусы берутся текущие. Сумма выполненных заказов не является подтверждением фактической оплаты. Старые заказы попадают в показатели, если их дата входит в диапазон; посещения задним числом не восстанавливаются.

В «Настройки сбора» можно выключить аналитику, исключить вошедшего администратора и выбрать часовой пояс: Asia/Novosibirsk (по умолчанию), Europe/Moscow или UTC. После включения обновите уже открытые страницы сайта. Административные страницы не инструментированы. Для проверки посещений при включённом исключении администратора откройте сайт в другом профиле/приватном окне. Do Not Track и Global Privacy Control отключают сбор.

Идентификатор браузера случайный, хранится в localStorage до 30 дней; при недоступном хранилище используется память страницы. Сессия общая для вкладок одного origin, обновляется после 30 минут без событий и не дольше 24 часов подряд. Очистка хранилища, блокировщики, закрытие страницы до отправки, ограничения браузера и подмена событий влияют на показатели: это приблизительные браузерные метрики, не подтверждённые люди. Повторное событие с тем же event_id сохраняется один раз. Аналитика не блокирует оформление заказа при ошибке сбора.

В событиях нет контактов, поисковых параметров, fragment, полного referrer или User-Agent. Сохраняются публичный путь, домен первого источника сессии, категория устройства/браузера, серверное время и HMAC идентификаторов. Технический лимит использует HMAC IP, а не сам адрес. Сырые UUID не записываются. События и сессии удаляются через 90 дней при запуске и каждые 6 часов; связи со старыми заказами обнуляются без удаления заказов. Резервные копии PostgreSQL могут содержать ранее сохранённые данные в рамках срока хранения копий. Ключ HMAC выводится из серверного ADMIN_API_KEY; его замена меняет идентификаторы будущих сессий.

API: публичные GET `/api/analytics/config`, POST `/api/analytics/collect`; административные GET `/api/admin/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD`, GET/PUT `/api/admin/analytics/settings`. Для collect нужны UUID v4 event_id/visitor_id/session_id, type (`pageview`, `cart_add`, `checkout_start`), публичный path и referrer-домен, заголовок `x-nova-analytics: 1`. Нельзя отправлять события на административные адреса. Максимум 2 КиБ на запрос и 120 событий с IP за 10 минут поверх общего лимита API. Время события задаёт сервер. Административные отчёты требуют сессию, изменения настроек — также CSRF. Отчёт читается одним согласованным снимком БД; одновременно допускается не более двух тяжёлых отчётов. Проверка: `npm test` (включая реальные SQL-запросы PostgreSQL через PGlite) и `npm run build`.


## Оплата NOVA 0.18

Раздел **Оплата** в админке содержит инструкции для ЮKassa, Т-Банка, CloudPayments, Robokassa, PayKeeper и другого сервиса. Это каталог способов подключения, а не пять нативных API-адаптеров. Модуль по умолчанию выключен, действующих реквизитов и демонстрационных платёжных форм в нём нет.

1. В кабинете выбранного сервиса получите готовую платёжную ссылку или **публичный** HTML/JavaScript/iframe-код. Завершите подключение магазина и настройки чека у провайдера.
2. Выберите сервис и режим в NOVA. Вставьте ссылку / код, заголовок и инструкцию покупателю. Добавьте точные HTTPS-источники ресурсов из официальной инструкции, включая индивидуальный домен PayKeeper и необходимые источники 3-D Secure. Предустановленные источники — стартовый список, не гарантия полного набора для каждого способа оплаты.
3. Предпросмотр открывается только вручную. Он использует пример N000001 / 100 ₽, **но не переводит провайдера в тестовый режим**. Используйте тестовый код из его кабинета. Не вставляйте API Secret, пароли и ключи подписи: содержимое виджета получает покупатель.
4. Сохраните настройки с включённой оплатой. После оформления заказа покупатель сможет открыть форму либо платёжную страницу в новой вкладке. Сверьте сумму и номер заказа. Статические подписанные формы/ссылки не пересчитываются автоматически для другой корзины.
5. Проверьте поступление полной суммы в кабинете сервиса. В **Заказы → карточка → Оплата** укажите номер операции / основание и подтвердите полную оплату. Для полного возврата сначала выполните его у провайдера, затем сохраните подтверждение в NOVA. Обе записи остаются в истории. Оплаченный заказ нельзя отменить с возвратом товара на склад до подтверждения полного возврата денег.

В коде виджета доступен только `window.NOVA_PAYMENT`: `order_number`, `amount` (рубли строкой с двумя знаками), `amount_cents`, `currency`. Контакты и ключ доступа к заказу туда не передаются. Использовать динамические параметры можно только если их поддерживает сам виджет. Подписанные запросы Robokassa и других API необходимо формировать на сервере отдельным адаптером. Нельзя переносить ключи подписи в JavaScript.

Виджет исполняется в отдельном iframe с непрозрачным origin. Изоляция намеренно не включает `allow-same-origin`: некоторые банковские SDK, cookies и 3-D Secure в таком режиме могут не работать; используйте резервную платёжную ссылку. Совместимость каждого реального виджета проверяется с тестовыми реквизитами продавца. Карточные данные обрабатывает форма провайдера. Сообщения JavaScript, возврат на сайт и нажатия кнопок не являются доказательством оплаты. В этом релизе нет автоматической проверки API/webhook, частичных оплат/возвратов, создания чеков или выполнения возврата из NOVA.

Публичная инструкция оплаты доступна только по подписанному ключу квитанции конкретного заказа через POST, до 30 дней после оформления. Повтор оформления с тем же UUID возвращает тот же ключ; сумма берётся из сохранённого заказа. При выключении модуля или отмене заказа открытие оплаты блокируется. Смена `ADMIN_API_KEY` аннулирует ранее выданные подписи.

При обновлении Nginx добавьте рядом с `/api/code-frame` точный маршрут:

```nginx
location = /api/payment-frame { include /etc/nova/code-frame-proxy.conf; }
```

Используется тот же proxy-файл, сохраняющий CSP ответа API; общий `/api/` proxy скрывает этот заголовок и для платёжного iframe не подходит. Главная CSP и существующий редактор кода не ослабляются. Все новые надписи покупателя доступны в **Оформление и код → Тексты → Оплата**.


## Формы обратной связи NOVA 0.19

В разделе **Формы и заявки** доступны конструктор, входящие обращения и каналы уведомлений. Приём по умолчанию выключен; секретов, получателей и фоновых тестовых сообщений в поставке нет.

1. Откройте **Почта и Telegram**. Укажите собственный SMTP, From и до 5 получателей; для Telegram — токен бота и один chat_id / @имя канала. Включите нужные каналы и общий приём, сохраните. Пустое поле секрета сохраняет прежнее значение; отдельный флажок удаляет его.
2. Нажмите кнопку теста нужного канала. Она отправляет фиксированное тестовое уведомление на **сохранённого** получателя. Результат появится во вкладке **Заявки**. Секреты вводите непосредственно в своей админке, не в коде страницы.
3. Создайте форму: до 10 полей (текст, email, телефон, сообщение, флажок), обязательность, порядок, тексты кнопки / результата / согласия и ссылка на политику. Выберите email, Telegram или оба канала, включите форму. Предпросмотр ничего не отправляет.
4. В **Страницы → редактор → + Форма обратной связи** выберите форму и опубликуйте страницу. Её можно назначить главной через общие настройки. На витрине форма работает только при включённом приёме и настроенных выбранных каналах. Действующие формы используют обновлённую конфигурацию без перепубликации страницы.
5. Во вкладке **Заявки** читайте полный текст, меняйте статус (новое / прочитано / обработано), проверяйте каждый канал отдельно. Письмо/сообщение содержит номер обращения и подписи полей. Заявка фиксируется до сетевой отправки; повтор после обрыва связи с тем же UUID не создаёт вторую заявку.

### Почтовые сервисы и 1Gb.ru

Обычный SMTP поддерживает TLS с начала соединения и обязательный STARTTLS, логин и пароль/ключ приложения. Есть пресеты Яндекс, Mail.ru, Gmail; фактические параметры, разрешение SMTP и пароль приложения сверяйте с кабинетом провайдера. OAuth не реализован. SMTP должен иметь публичный IPv4-адрес; внутренние/IP-адресные хосты и небезопасный TLS не поддержаны.

Профиль **1Gb.ru — отправка из скриптов** использует `robots.1gb.ru:25` без авторизации; From должен быть ящиком или псевдонимом на 1Gb.ru. По [официальной инструкции](https://www.1gb.ru/hosting_email.php), на VDS доступ к портам может потребовать обращения в поддержку; для внешнего SMTP с виртуального хостинга действует отдельная настройка. NOVA требует Node.js и PostgreSQL, одного PHP-хостинга недостаточно. Реле может работать без шифрования; обязательный TLS используйте через обычный SMTP при поддержке выбранного сервиса. SPF/DKIM/DMARC и ограничения почтовой службы настраиваются вне NOVA. From не подменяется адресом посетителя: его email передаётся в Reply-To.

### Telegram и очередь

Бот отправляет через фиксированный HTTPS Bot API Telegram, без произвольного API-адреса. Посетителям токен не передаётся. Для личного чата получатель должен начать разговор с ботом; для группы/канала нужны соответствующие права. Длинное уведомление сокращается до лимита Telegram с отметкой, полный текст остаётся в админке. Текст отправляется без Markdown/HTML-разметки и без предпросмотра ссылок.

Фоновый worker запускается вместе с API и проверяет очередь каждые 5 секунд. Каналы независимы; отключённый канал не блокирует другой. Успех означает приём сервисом, а не прочтение. Известные ошибки до отправки повторяются до 3 попыток с задержкой; для Telegram учитывается retry_after. При неоднозначном результате или прерывании процесса во время отправки ставится **Результат неизвестен** без автоматического повтора. Администратор может явно повторить неуспешное/частичное уведомление с текущими сохранёнными адресами и секретами, подтвердив риск дубликата. Успешный второй канал при этом не отправляется заново.

Секреты настроек и очереди зашифрованы AES-256-GCM с ключом, производным от `ADMIN_API_KEY`; случайный nonce и проверка целостности обязательны. После успешного приёма сервисом копия секретов в задании удаляется. Изменение `ADMIN_API_KEY` требует повторного ввода секретов, а незавершённые задания затем можно повторить с новыми настройками. Серверный ключ храните и резервируйте отдельно от базы. Учтите, что скомпрометированный сервер с этим ключом способен расшифровать сохранённые настройки.

У формы есть обязательное согласие, ловушка для ботов, подписанный короткоживущий challenge, проверка Origin/специального заголовка, лимит 5 новых обращений с IP за 15 минут и общий бюджет 100/сутки. Это базовая защита, а не полноценная CAPTCHA или гарантия отсутствия спама. Публичный ответ не раскрывает содержимое, получателей или каналы. IP хранится только в HMAC-лимите. Источник ограничен pathname, query/fragment и контакты не передаются в аналитику.

Хранение заявок настраивается на 30–365 дней (по умолчанию 90); очистка проходит каждые 6 часов, включая очереди. Отключение приёма приостанавливает отправку, но не очистку по сроку. Резервные копии имеют собственный срок. Выберите подходящие тексты согласия и политики для своего сайта и получателей данных. При обновлении обязательно установите зависимости по `package-lock.json`: добавлен Nodemailer. Новых сетевых портов или ослабления CSP входящего сайта не требуется.


## Темы и шаблоны NOVA 0.20

Раздел **Темы и шаблоны** устанавливает переносимые JSON-пакеты `nova-theme` и `nova-template` с API 1. Установка не меняет витрину: тему надо применить к черновику, проверить и отдельно опубликовать в **Оформление и код**. Применение сохраняет предыдущую версию оформления и оставляет тексты/данные сайта. Пакет можно экспортировать, настроить локальные формы/изображения и редактировать код шаблонов в админке.

Тема содержит стиль, до 20 параметров владельца и места header, home, catalog, product, page, blog, post, footer. HTML/CSS/JS изолированы; разрешён ограниченный API чтения и действия штатной корзины / формы после нажатия пользователя. Шаблон страницы заполняет секции редактора, не переносит товары или реквизиты. Встроенные примеры не включаются автоматически при обновлении. По умолчанию остаётся прежнее оформление.

Исходники примеров, CLI упаковки (`npm run theme:pack -- каталог файл.nova.json`) и [полное руководство](docs/THEMES.md) находятся в репозитории. Пакеты не могут устанавливать серверный код, зависимости, архивы или ослаблять CSP. Корзина, оформление заказа, оплата, обращения и секреты продолжают обслуживаться CMS. Ресурсы из медиатеки и формы привязываются на конкретном сайте.
