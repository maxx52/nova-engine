# Обновления и резервные копии NOVA 0.21

## Возможности и границы

В админке откройте **«Обновления и копии»**. Раздел показывает установленную версию, последний стабильный GitHub Release, описание и время проверки. Проверяются опубликованные релизы `vX.Y.Z`, а не коммиты ветки main. Черновики, prerelease и произвольные ссылки не устанавливаются.

С локальным менеджером доступны создание полной копии, проверка, расписание, обновление и восстановление. Проверка GitHub выполняется раз в сутки и по кнопке; **установка новой версии автоматически без нажатия владельца не начинается**. При недоступном GitHub сохранённая информация остаётся видна с сообщением об ошибке.

Текущий менеджер предназначен для Linux VDS с **native Node.js/systemd + PostgreSQL 17 в локальном Docker**. Это схема `nova.maxxdev.ru`. Docker-установка всей CMS и управляемый Node.js-хостинг без этой службы показывают проверку релизов и инструкцию обратиться к администратору. Не монтируйте Docker socket в контейнер веб-приложения и не запускайте API от root для включения кнопки обновления.

## Как работает обновление

1. Менеджер самостоятельно находит указанный опубликованный релиз **только** `maxx52/nova-engine`. HTTP-запрос из админки передаёт номер версии, без URL, команды или пути.
2. Загружает `nova-release.json` и пакет `nova-X.Y.Z.tar.gz`, сверяет размер, SHA-256 и совпадение метаданных с кодом. Проверяет Node.js, минимальную версию, API тем 1, схему/протокол менеджера 1.
3. Распаковывает только безопасные пути в отдельный каталог, устанавливает зависимости по lock-файлу от непривилегированного пользователя с `--ignore-scripts` в отдельной временной systemd-службе. У неё отдельная cgroup, ограничение времени/памяти и запись только в staging-каталог, проверяет sharp. Сборки интерфейсов уже включены в пакет. После установки зависимостей каталог блокируется от записи пользователем приложения, сверяются исходные файлы пакета и снимаются специальные биты доступа.
4. Создаёт флаг обслуживания и останавливает единственный API-процесс. Фоновые очереди и записи этого приложения приостановлены.
5. Создаёт полную копию, проверяет её восстановлением в отдельную временную PostgreSQL-базу, проверяет распаковку архивов и SHA-256. Рабочая база при проверке не заменяется.
6. Устанавливает код и интерфейсы, запускает API с миграциями, проверяет готовность. Снимает обслуживание после завершения.
7. Если установка/запуск не удались, восстанавливает базу, код, uploads, интерфейсы и env из проверенной копии. Если упала сама служба/сервер, при следующем запуске менеджер обрабатывает журнал незавершённой операции.

Не закрывайте SSH-сеанс с ручным отладочным процессом вместо сервиса: менеджер должен работать через systemd. Окно админки можно оставить открытым; во время остановки API она показывает временную недоступность и продолжает опрос. После восстановления более старой базы может потребоваться снова войти.

SHA-256 обнаруживает повреждение, но **не заменяет независимую цифровую подпись**. Источник доверия в первой версии — наш репозиторий/аккаунт GitHub и HTTPS. Компрометация выпуска релизов способна привести к установке вредоносного кода. Доступ к публикации релизов должен быть ограничен; удалённые shell-команды, сторонние URL и автоматическая установка main не поддерживаются.

## Что входит в копию

| Данные | Содержимое |
| --- | --- |
| PostgreSQL | Полный custom-format pg_dump базы NOVA |
| Uploads | Каталог файлов, на который ссылается база |
| Код | Приложение, его runtime-зависимости и конфигурация версии; без `.git`, корневого `.env` и uploads |
| Витрина и админка | Управляемые публичные пути `index.html`, `assets`, `admin` |
| Серверные секреты | Отдельная копия настроенного env-файла с исходными правами и владельцем |
| Метаданные | Дата, версия, причина, контрольные суммы, размер, факт проверки восстановления |

Сохраняются темы, страницы, товары, заказы, покупатели, интеграции и их ключ шифрования. Nginx-конфигурация, SSL-сертификаты, ОС и другие сайты не входят в эту копию. База предназначена для единственного API-процесса: менеджер не может согласованно копировать сайт, если в ту же базу/файлы одновременно пишет другое приложение.

Копии находятся вне webroot, доступны только root. API/браузер получает только метаданные, а не содержимое архивов или env. Перед восстановлением введите **ВОССТАНОВИТЬ** и подтвердите дату: более новые заказы/изменения будут заменены. Перед заменой менеджер создаёт и проверяет отдельную копию текущего состояния.

Ежедневные копии задаются часом **UTC**. Новосибирск — UTC+7: для 03:00 по Новосибирску выберите 20:00 UTC предыдущего дня. Хранение — 7/14/30 дней; очистка выполняется после успешной копии, две последние завершённые копии сохраняются. Ошибки видны в журнале; неудачная ежедневная копия автоматически не повторяется в тот же день.

**Локальная копия не защищает от потери VDS.** Настройте зашифрованное внешнее хранение через инфраструктуру хостинга или отдельное задание администратора. Автоматическая выгрузка во внешнее облако в 0.21 не реализована. Сроки хранения внешних копий задаются отдельно. Эти копии содержат персональные данные и секреты.

## Подключение службы администратором сервера

Требуется Linux/systemd, Python 3.11+, Docker CLI с доступом к локальному PostgreSQL-контейнеру, pg_dump/pg_restore внутри него, Node.js/npm и отдельный пользователь приложения. Достаточно места для staging и нескольких полных копий, а также для временной проверочной базы PostgreSQL. Проверяйте фактическую свободную ёмкость: с ростом базы и uploads она должна увеличиваться.

1. Установите/проверьте CMS 0.21. Для первой установки службы можно подготовить её на 0.20, затем установить 0.21 через локальный клиент администратора.
2. Из проверенного исходного кода скопируйте менеджер в защищённый каталог:

```bash
sudo install -d -m 755 /usr/local/lib/nova-updater
sudo install -m 644 deploy/updater/agent.py /usr/local/lib/nova-updater/agent.py
sudo install -d -m 750 /etc/nova
sudo install -m 600 deploy/updater/config.example.json /etc/nova/updater.json
```

Код приложения и публичный webroot, включая управляемые assets/admin, должны принадлежать root и быть доступны приложению/веб-серверу только на чтение. Их родительские каталоги также должны принадлежать root без групповой/общей записи. Пользователь приложения записывает только uploads; менеджер не стартует при небезопасных правах корневых путей. На существующем VDS администратор сначала проверяет отсутствие посторонних ссылок и нормализует права только каталогов NOVA.

3. Отредактируйте **root-owned** `/etc/nova/updater.json`. Пример относится к нашему VDS; замените все пути, имя сервиса/контейнера/базы, пользователя и группу. `db_admin` нужен только менеджеру, API остаётся с `nova_app`. Каталоги app/web/uploads/state/backups/staging должны быть разными и не вложенными. Секретов в JSON нет — только путь к существующему env-файлу. В service unit открыт на запись `/etc/nova` для восстановления env; если env находится в другом каталоге, адаптируйте `ReadWritePaths`. `ProtectHome=true` требует размещать приложение и копии вне `/home` и `/root`, как в примере. Менеджер не создаёт пользователя, базу или API-service автоматически.
4. Подключите режим обслуживания в **существующем HTTPS server-блоке** соответствующего сайта, подставив реальный webroot:

```nginx
if (-f /www/wwwroot/nova.maxxdev.ru/.nova-maintenance) { return 503; }
```

Для обычного nginx есть [пример одного домена](../deploy/nginx.single-domain.conf.example). Сохраните прежний конфиг, проверьте `nginx -t`, затем reload. Только домен NOVA, без изменений других сайтов.
5. Установите сервис:

```bash
sudo install -m 644 deploy/updater/nova-updater.service /etc/systemd/system/nova-updater.service
sudo systemctl daemon-reload
sudo systemctl enable --now nova-updater
```

Служба использует root для копирования, Docker и переключения сервиса. Код самой службы находится вне каталога, доступного пользователю CMS, и **не заменяется обновлением сайта**. Новые несовместимые версии протокола потребуют ручного обновления службы. При установке менеджера используйте исправление 0.21.2 или новее: оно запускает подготовку через ограниченную задачу systemd вместо переключения UID внутри защищённой службы и проверяет права публичных сборок при закрытом umask.
6. В окружении **API-сервиса** добавьте `NOVA_UPDATER_SOCKET=/run/nova-updater/agent.sock`. Например, через systemd drop-in для своего API:

```ini
[Service]
Environment=NOVA_UPDATER_SOCKET=/run/nova-updater/agent.sock
```

Перечитайте systemd и перезапустите только API NOVA. Unix-сокет root:группа-приложения, права 660, родитель 750; менеджер дополнительно проверяет UID подключившегося процесса. TCP-порт управления не открывается. Не добавляйте посторонних пользователей в группу приложения.
7. Откройте админку, создайте копию и убедитесь, что проверка успешна. Только после этого включайте ежедневное расписание. Проверяйте копии после изменений инфраструктуры.

API-операции требуют административную сессию, CSRF и допустимый origin. Команды ограничены `check`, `backup`, `verify`, `update`, `restore`, `schedule`; невозможно передать shell-строку, путь восстановления, URL архива или другой systemd-сервис через веб-интерфейс.

## Локальный клиент и диагностика

Из корня проверенных исходников, от root или пользователя приложения:

```bash
python3 scripts/system-client.py status
python3 scripts/system-client.py check
python3 scripts/system-client.py backup
python3 scripts/system-client.py verify 20261018T100000Z-abcdef12
python3 scripts/system-client.py update 0.21.0
```

ID выше — пример, используйте реальный ID из `status`. Обновление требует более новой версии. Восстановление (`restore ID --confirm ВОССТАНОВИТЬ`) заменяет данные и предназначено только для осознанной операции администратора. Из браузера оно требует отдельного подтверждения.

Журнал службы: `journalctl -u nova-updater`. Закрытый журнал команд: `/var/lib/nova-updater/worker.log`; не публикуйте его без проверки. Во время работ API может отвечать 503. При неудачном откате флаг обслуживания сохраняется — требуется восстановление администратором, а не принудительное открытие сайта поверх частично восстановленной базы.

Копии, журнал и настройки службы переживают обновление приложения. Не удаляйте эти каталоги для «исправления ошибки». Ненужные staging-каталоги после аварий удаляет администратор после проверки, что операция завершена. Прерванная проверка может оставить отдельную базу с префиксом `nova_verify_`; администратор удаляет её только убедившись, что менеджер не работает с ней.

## Выпуск релиза на GitHub

Исходный код содержит `config/release.json` — общий номер продукта и требования. `config/release.js` используется админкой и API. Рабочие версии workspace-пакетов не являются номером релиза продукта.

1. Подготовьте `config/release.json` и `docs/releases/X.Y.Z.md`, обновите README.
2. Выполните проверки и сборку. Для ручной проверки пакета:

```bash
npm ci
npm test
python3 -m unittest discover -s deploy/updater/tests -v
npm run build -w @nova/storefront
npm run build -w @nova/admin -- --base=/admin/
node scripts/build-release.mjs /tmp/nova-release
```

3. После ревью создайте ветку **`release/vX.Y.Z`** на нужном commit. Её push запускает Security and build, включая контейнерные проверки и реальное восстановление дампа во временную PostgreSQL 17-базу. Только после успеха отдельный workflow публикует GitHub Release `vX.Y.Z` с манифестом и готовым пакетом. Проверка ветки/версии/репозитория выполняется до публикации.
4. Не переписывайте опубликованный тег и не заменяйте его assets: исправление выпускайте следующим patch-релизом. Для публикации используются ограниченные права GitHub Actions на содержимое этого репозитория; общий PAT в CMS не нужен.

Примечание: GitHub не гарантирует совместимость произвольного пользовательского кода с новой CMS. В версии 0.21 API тем не меняется, пакеты с другим API не принимаются. Перед будущими крупными релизами проверяйте свои темы и интеграции на отдельной тестовой установке.
