# Установка NOVA CMS на хостинг

Руководство для NOVA Engine 0.20. Сначала проверьте [системные требования](REQUIREMENTS.md). Инструкция описывает текущее приложение; наличие Node.js в рекламе хостинга само по себе не подтверждает совместимость.

## 1. Как выбрать способ размещения

| Ваш вариант | Способ установки |
| --- | --- |
| Новый Linux VDS с root, свободными 80/443 | [Установщик одной командой](INSTALL.md) |
| VDS с aaPanel, ISPmanager или уже работающим nginx | Ручное развёртывание в отдельном каталоге и настройка одного виртуального хоста; существующие сайты не останавливаются |
| Управляемый Node.js-хостинг с PostgreSQL и настройкой маршрутов | Ручная установка без Docker по шагам ниже; постоянный процесс запускает менеджер хостера |
| Только PHP/MySQL/FTP или только статические сайты | NOVA целиком не запустится; нужен другой тариф либо VDS |

Docker и root не обязательны, если хостер предоставляет нужные Node.js, PostgreSQL, HTTPS, маршрутизацию и постоянное файловое хранилище.

## 2. Подготовить домен и базу

В панели создайте сайт и подключите HTTPS. Для примера используем `https://shop.example.ru` и админку `https://shop.example.ru/admin/` — один origin, без настройки CORS между разными доменами.

Создайте **пустую PostgreSQL 17** и отдельного пользователя приложения. У пользователя должны быть права миграции в своей базе/схеме и отсутствовать административные привилегии из [требований](REQUIREMENTS.md). Не используйте `postgres` или другого суперпользователя в `DATABASE_URL`: production-API откажется запускаться. Таблицы создаёт сама CMS при старте.

Запишите адрес базы, порт, имя базы, пользователя, пароль и параметры TLS. На управляемом хостинге эти значения берутся из кабинета; адрес PostgreSQL не обязан совпадать с адресом сайта. Не подставляйте данные локальной базы из `.env.example`.

## 3. Загрузить исходники и собрать интерфейс

Подключитесь по SSH как пользователь сайта. Ниже `~/nova-engine` — **новый отдельный каталог приложения вне публичной папки**, не каталог другого сайта.

```bash
git clone https://github.com/maxx52/nova-engine.git "$HOME/nova-engine"
cd "$HOME/nova-engine"
node --version
npm --version
npm ci
npm run build -w @nova/storefront
npm run build -w @nova/admin -- --base=/admin/
```

Если квоты хостинга не позволяют сборку, соберите интерфейсы на своей машине или CI и загрузите **оба dist**. На самом сервере всё равно нужны исходники API и production-зависимости; их устанавливают под серверную ОС/архитектуру:

```bash
cd "$HOME/nova-engine"
npm ci --omit=dev
```

Не переносите Windows `node_modules` на Linux. `sharp` содержит платформенные компоненты. Даже при сборке на другом компьютере API не превращается в статический сайт.

## 4. Настроить переменные окружения

Воспользуйтесь защищёнными переменными панели или создайте `.env` **в корне приложения**, вне публичного webroot:

```bash
cd "$HOME/nova-engine"
umask 077
cp .env.example .env
chmod 600 .env
openssl rand -hex 32
```

Последняя команда создаёт собственный секрет. Запишите его как `ADMIN_API_KEY`, не используйте значение из примера. Если переменные передаются панелью, `.env` не нужен; не оставляйте две противоречивые конфигурации.

Пример имён параметров (значения нужно заменить):

```dotenv
NODE_ENV=production
DATABASE_URL=postgres://nova_app:YOUR_URL_ENCODED_PASSWORD@DB_HOST:5432/nova
ADMIN_API_KEY=YOUR_RANDOM_64_HEX_CHARACTERS
ADMIN_ORIGINS=https://shop.example.ru
SESSION_SECURE=true
API_HOST=127.0.0.1
PORT=3001
TRUST_PROXY=loopback
UPLOAD_DIRECTORY=/ABSOLUTE/PRIVATE/PATH/nova-uploads
LOG_LEVEL=info
```

- `API_HOST`, `PORT` и `TRUST_PROXY` — **пример для локального nginx**, не универсальные значения для всех хостеров. При внешнем прокси получите его адреса у поддержки и укажите только их. Не задавайте `TRUST_PROXY=true`.
- Для удалённой PostgreSQL добавьте согласованные параметры TLS к URL, например `?sslmode=verify-full` при сертификате, которому доверяет окружение. Специальные символы пароля в URL кодируются. Не отключайте проверку сертификата.
- Создайте каталог uploads, доступный на запись пользователю Node.js. Он должен переживать обновления и перезапуски; его нельзя раздавать как обычную исполняемую папку сайта.
- `ADMIN_API_KEY` нужен для первоначальной настройки и шифрования настроек интеграций. Сохраните его вместе с резервными копиями; случайная замена нарушит расшифровку сохранённых SMTP/Telegram-секретов.

## 5. Запустить API и включить автозапуск

Первый запуск для проверки, из корня проекта:

```bash
node apps/api/src/server.js
```

В другом SSH-сеансе проверьте API на указанном локальном порту, например:

```bash
curl --fail http://127.0.0.1:3001/health
```

Ожидается `{"status":"ok"}`. Если процесс завершается, прочитайте журнал: обычно причина в роли/доступе PostgreSQL, переменных окружения или правах uploads. Не публикуйте журналы с секретами.

Остановите проверочный процесс через Ctrl+C. В панели Node.js / менеджере процессов укажите:

| Настройка | Значение |
| --- | --- |
| Рабочий каталог | Полный путь к `nova-engine` |
| Команда | `node apps/api/src/server.js` |
| Количество экземпляров | 1 |
| Среда | production и переменные из предыдущего шага |
| Автозапуск / перезапуск | Включён, процесс остаётся работать без SSH-сеанса |
| Журналы | Включены, с ограничением размера и ротацией |

На VDS это может быть systemd или менеджер панели; на виртуальном хостинге — штатный диспетчер хостера. Не запускайте одновременно два менеджера для одного API. `nohup` и открытая SSH-вкладка не заменяют управляемый сервис.

## 6. Подключить витрину, админку и API

Маршруты **обязательны**. Настройте их в панели или передайте администратору/поддержке:

| URL | Что обслуживает |
| --- | --- |
| `/api/…` | API Node.js; сохранять путь, передавать cookies и разрешать необходимые методы, не кэшировать |
| `/api/code-frame`, `/api/payment-frame` | Точные маршруты Node.js; сохранить его CSP с nonce и sandbox, не добавлять CSP обычной страницы поверх |
| `/uploads/…` | API Node.js, который проверяет и отдаёт изображения; сохранить CORP для изображений в теме |
| `/admin` | Перенаправление на `/admin/` |
| `/admin/…` | Статика из `apps/admin/dist`; `/admin/assets/…` — реальные файлы, остальные маршруты админки возвращают её `index.html` |
| Остальные пути | Статика из `apps/storefront/dist`, при отсутствии файла — её `index.html` для маршрутов `/catalog`, `/product/…`, страниц и блога |

Используйте отдельный **публичный каталог**, содержащий только файлы собранных интерфейсов. Например, скопируйте содержимое `apps/storefront/dist/` в webroot и `apps/admin/dist/` — в его подпапку `admin/`. Не назначайте весь репозиторий webroot: там есть `.env`, исходники и служебные файлы.

Для nginx на VDS используйте [пример для одного домена и `/admin/`](../deploy/nginx.single-domain.conf.example). Замените домен, пути сертификата, webroot и пути к snippets. Пример ожидает исходники в `/srv/nova/app`, публичные сборки в `/srv/nova/public`, API на `127.0.0.1:3001`. Если приложение установлено в домашнем каталоге, используйте реальные абсолютные пути и убедитесь, что пользователь nginx может читать только публичные файлы.

В aaPanel настройка вносится в виртуальный хост нужного сайта: сначала сохраните прежнюю конфигурацию, подключите сертификат в панели, затем адаптируйте **содержимое его server-блоков**, не добавляя дублирующие server_name/listen. У существующего сайта могут быть правила ACME и панели — их сохраняет администратор. Snippets `api-proxy.conf`, `code-frame-proxy.conf` и `public-media-proxy.conf` рассчитаны на порт 3001; при другом порту измените их копии. На VDS проверьте `nginx -t` перед reload. Этот шаблон требует проверки в конкретной конфигурации панели; он не был применён автоматически к работающим сайтам.

[Старый пример с двумя доменами](../deploy/nginx.conf.example) использует другие ограничения публичного API и не предназначен для копирования целиком в эту схему магазина.

Внешний прокси должен заменять IP/HTTPS forwarding-заголовки; приложение доверяет именно его адресам. Включите HTTPS-перенаправление, лимит запроса от 6 МБ и security-заголовки обычных HTML-страниц из `deploy/security-headers.conf`. На специальных iframe-маршрутах действуют заголовки самого API. Если панель умеет только проксировать **все** запросы в один Node.js-процесс, текущей команды запуска NOVA недостаточно: API сам не раздаёт собранные интерфейсы. Нужна настройка маршрутов хостером; отдельный адаптер для такого режима пока не включён в CMS.

## 7. Создать администратора и проверить работу

1. Откройте `https://shop.example.ru/admin/`, введите собственный `ADMIN_API_KEY` в форму первоначальной настройки и создайте логин/пароль.
2. Выйдите и войдите снова: это проверяет HTTPS/cookies.
3. Добавьте тестовый товар и изображение, проверьте каталог и карточку на витрине, обновите страницу по прямому URL.
4. Проверьте предпросмотр темы и открытие формы. Перед тестовой отправкой email/Telegram подключайте только свои каналы и получателей.
5. Убедитесь, что `/api/admin/packages` без входа отвечает 401, `.env` недоступен из интернета, а внутренние порты не опубликованы напрямую.
6. Перезапустите управляемый процесс. Настройки, товары и изображения должны сохраниться.
7. Настройте резервные копии PostgreSQL, uploads и секретов вне сервера; проверьте восстановление на отдельной установке. Обновления выполняйте после копии базы и файлов, с сохранением предыдущей версии кода.

## 8. Особенности 1Gb.ru

По официальной инструкции **Node.js v2** хостинг предоставляет Node-инструменты и направляет HTTP(S)-запросы в приложение на **3000**. Поддержка включается через «Полный список функций → HTTP службы». Постоянный запуск задаётся в `~/conf.d/node`, управляется через `~/init.d/node`, журналы находятся в `~/logs_node`. Это описание услуги провайдера; успешная установка NOVA на конкретный тариф **ещё не проверена**.

После согласования маршрутизации из раздела 6 и версии Node.js:

```dotenv
PORT=3000
```

Остальные `API_HOST` и `TRUST_PROXY` согласуйте с поддержкой, не переносите настройки loopback с VDS вслепую. Для приложения в `~/nova-engine` настройки диспетчера по документации 1Gb.ru:

```bash
NODE_DIR="nova-engine"
NODE_START="node apps/api/src/server.js"
```

И команды управления:

```bash
~/init.d/node start
~/init.d/node status
~/init.d/node stop
```

**До запуска** проверьте, что этот сервис не обслуживает другой ваш сайт. Не перезаписывайте существующий `~/conf.d/node` без проверки. Поддержка может предложить отдельный аккаунт/окружение для приложения.

В кабинете PostgreSQL создаётся отдельно. Хостер указывает адрес своей базы в кабинете и публикует поддержку PostgreSQL 17, но наличие базы не подтверждает все требуемые права конкретного пользователя. Версию Node.js и лимиты тарифа уточните отдельно.

Если 1Gb.ru не сможет настроить раздельную раздачу статики и проксирование API с нужными заголовками, используйте VDS либо другой совместимый Node.js-хостинг. Это ограничение текущего способа развёртывания NOVA, а не утверждение, что у 1Gb.ru нет Node.js.

Официальные источники (проверены 18.10.2026):

- [Node.js — быстрый старт v2](https://www.1gb.ru/wiki.php?title=Node.js_—_быстрый_старт_v2).
- [Техническое описание услуг, SSH и PostgreSQL](https://www.1gb.ru/services.php).
- [Параметры среды, версии PostgreSQL](https://api.1gb.ru/services_compatability.php).

## 9. Типичные проблемы

| Симптом | Что проверить |
| --- | --- |
| На сайте JSON/404 вместо витрины | Все пути попали в API; нужна раздача dist и маршруты из раздела 6 |
| Пустая админка / ошибки загрузки JS | Сборка с `--base=/admin/`, расположение `admin/assets`, CSP и отсутствие старого HTML в кэше |
| Бесконечное «Проверка подключения» / 502 | Запущен ли API, правильный порт, путь `/api/`, доступ к базе и журнал процесса |
| Вход не сохраняется / запрос отклонён | HTTPS, точный `ADMIN_ORIGINS`, cookies, заголовки прокси, отсутствие кэширования API |
| Тема/редактор кода не отображается | Отдельные CSP/sandbox для code-frame/payment-frame; панель/CDN не должны заменять их общим CSP |
| Изображения не загружаются | Права и постоянство uploads, маршрут через Node.js, лимиты запроса и поддержка `sharp` |
| Формы принимаются, но уведомления не уходят | Работает ли постоянно API, исходящие SMTP/HTTPS, настройки и очередь в админке |

Письма через 1Gb.ru настраиваются отдельно в разделе «Почта и Telegram»: особенности почтового реле не заменяют требования к запуску самой CMS. [Подробности интеграций](../README.md).

## SEO и публичный HTML

Начиная с 0.23 для индивидуальных метатегов в исходном HTML, корневых sitemap.xml/robots.txt, HTTP-редиректов и 404 публичные страницы направляются в API. Админка и assets остаются статическими. Существующий nginx не меняется при обновлении приложения: [порядок подключения SEO](SEO.md#подключение-на-хостинге).
