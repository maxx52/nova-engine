# NOVA Booking & CRM: аудит и первый этап

Аудит выполнен для main на df43a3437b9edb453debb2be9ddd7892d041710e. Стек: Node.js/Fastify, Vue/Vite, PostgreSQL через pg и параметризованные SQL-запросы; ORM нет. Схема ядра инициализируется при запуске функциями init*. Уже есть сессии, CSRF, роли, 2FA, audit, формы/email/Telegram, платежи, аналитика, редактор, резервные копии и обновление NOVA. Эти возможности могут быть использованы повторно после проверки их совместимости с изоляцией организаций. Механизм тем не является загрузчиком серверного кода; универсального установщика серверных расширений не обнаружено.

## Границы и порядок развития

- `apps/api/src/booking/` — отдельное пространство модуля: миграции и API фундамента. Сейчас это встроенный opt-in модуль, а не отдельный архив расширения. Новые функции следует добавлять в отдельные подпакеты booking, crm, staff, communications, telephony, marketing, automation, payments, reports и profiles.
- `apps/admin/src/BookingWorkspace.vue` — первый раздел админки; API аутентифицируется существующей сессией. Членство в конкретной организации и роль в ней проверяются дополнительно на сервере. Владелец NOVA создаёт организацию и становится её владельцем; менеджер и наблюдатель назначаются через интерфейс или API. Глобальная роль NOVA также должна разрешать доступ к маршруту. Редактору доступ запрещён.
- Планируемый поток: виджет → Booking API → транзакция PostgreSQL → события в outbox → очередь → CRM, коммуникации и аналитика. Для исходящих интеграций потребуются идемпотентность и повторные попытки. Это план, не реализованный функционал.
- Каждая последующая миграция должна иметь новый номер и выполняться в транзакции под advisory lock. Версия 1 добавляет изолированные таблицы организаций, членства и филиалов; повторный запуск безопасен. Записи модуля не удаляются при выключении. Откат схемы и независимый установщик/обновление не реализованы. До изменения базы создавайте и проверяйте резервную копию.
- Для будущего календаря нужны транзакционные ограничения пересечений (включая удержания и все ресурсы), тесты гонок на настоящем PostgreSQL и правила часовых поясов. PGlite не заменяет такую проверку. Вынесение данных в будущий SaaS требует отдельной проверки всей цепочки доступа, фоновых заданий, резервных копий и хранилищ.
- Медицинские карты и диагнозы не хранятся. Юридическое соответствие обработке персональных данных требует отдельной оценки и организационных мер.

## Установка и проверка первой части

1. Создайте резервную копию и сначала используйте тестовую копию NOVA и базы.
2. Установите изменения проекта, выполните `npm ci` и `npm run build`. В конфигурации API установите `NOVA_BOOKING_ENABLED=true`, затем перезапустите API. Первая миграция применится при старте. Для выключения уберите переменную и перезапустите API; таблицы сохраняются.
3. Войдите как владелец, откройте «Booking & CRM», создайте организацию и филиал. Укажите IANA timezone, например `Asia/Barnaul`.
4. Обновите страницу и убедитесь, что данные сохранились. Неверный часовой пояс должен отклоняться. Другая учётная запись без членства не должна видеть организацию. API членства: `POST /api/admin/booking/organizations/:orgId/members` с `{"user_id":"2","role":"viewer"}` или `manager`, используя существующие сессию и CSRF. Название и профиль организации, а также данные филиала можно изменять. В разделе «Доступ к организации» можно назначить или отозвать доступ; ID пользователя показан в разделе «Доступ и безопасность». Доступ проверяется при каждом запросе. Глобальная роль NOVA и её существующие разрешения остаются в силе. Списки организаций, филиалов и участников выводятся страницами по 50 записей.
5. Запустите `node --test apps/api/test/booking.test.js`, `npm test` и `npm run build`.

Статус: это только часть первого этапа; нет публичной записи, сотрудников, услуг и календаря. Реализованы назначение и отзыв участников, но миграция, права и интерфейс ещё требуют проверки в установленной NOVA с настоящим PostgreSQL. На VDS проверены параллельный запуск первой миграции, сессии, CSRF и доступ между организациями на отдельной базе PostgreSQL 17. Интеграции, независимые обновления, браузерная проверка и полностью проверенная SaaS-изоляция отсутствуют. Не используйте как готовую CRM или для персональных данных клиентов.

## Управление схемой модуля

После установки файлов текущей версии Booking доступны команды `node scripts/booking-schema.mjs status`, `install` и `upgrade`; они используют `DATABASE_URL` из окружения или `.env` NOVA. `status` только читает состояние, `install` идемпотентно применяет отсутствующие миграции, `upgrade` требует предварительной установки. Миграции выполняются в транзакции под блокировкой PostgreSQL. Если обнаружена неизвестная версия или пропуск в истории, запуск отклоняется, данные не удаляются. Перед обновлением необходимо проверить резервную копию и совместимость.

Это управление только схемой БД: отдельный установщик файлов, независимое обновление серверного кода и интерфейса и откат кода ещё не реализованы. Для показа раздела по-прежнему требуются файлы этой ветки, сборка админки и `NOVA_BOOKING_ENABLED=true`. Не считайте CLI завершённым механизмом установки расширения.

## Экспериментальный пакет модуля

`node scripts/booking-package.mjs build <новый-каталог>` формирует пакет исходников с манифестом; `node scripts/booking-package.mjs verify <каталог>` проверяет структуру, размеры и контрольные суммы. Каталог назначения не должен существовать. Команда `sign <каталог> <закрытый-ключ-Ed25519>` добавляет подпись манифеста; `verify-trusted <каталог> <доверенный-открытый-ключ>` проверяет подпись и хеши файлов. Открытый ключ должен быть получен и закреплён отдельно от пакета. Закрытый ключ хранится вне сервера клиента и репозитория. Простая команда `verify` проверяет только целостность, а не подлинность. Проверка ещё не подключена к установщику: не исполняйте неизвестные пакеты. В пакете исходник компонента Vue, а не автономный исполняемый интерфейс. Установщика и переключения версий на сервере пока нет.

## Подготовка проверенного пакета

`node scripts/booking-stage.mjs <каталог-пакета> <каталог-хранилища> <открытый-ключ>` проверяет подпись и хеши, копирует пакет во временный каталог и повторно проверяет копию. После этого пакет переносится в `booking-<версия>`. Существующую версию команда не перезаписывает. Каталог хранилища должен существовать, принадлежать текущему пользователю и не быть доступным для записи группе или остальным. При аварийном завершении блокировку `.booking-stage.lock` должен проверить администратор.

Это подготовка файлов: она не устанавливает и не загружает код, не включает модуль и не изменяет БД. Проверочный ключ должен быть доверен вне пакета. Пакет содержит исходный Vue-компонент, а не автономно загружаемый интерфейс. Полностью независимые установка, переключение и откат пока не реализованы.

## Экспериментальный серверный загрузчик

При включённом `NOVA_BOOKING_ENABLED=true` можно выбрать подготовленную версию, задав одновременно `NOVA_BOOKING_PACKAGE_STORE`, `NOVA_BOOKING_PACKAGE_VERSION` и `NOVA_BOOKING_TRUSTED_KEY`. При запуске API проверяет права на каталог и файлы, подпись с отдельно размещённым ключом, состав, хеши, версию пакета и точную версию NOVA. Неверная или неполная конфигурация прерывает запуск API; требуется перезапуск, горячая замена не поддерживается. Оператор и пользователь службы должны заранее обеспечить безопасные права на файлы и ключ. Служба загружает серверный код только после проверки.

Это экспериментальная серверная часть: административный компонент по-прежнему включён в сборку админки NOVA. Нет автоматического отката, переключения интерфейса, доверенного распространения ключей и проверки обновления между версиями. Не использовать для клиентских данных.

## Экспериментальное переключение серверной версии

После подготовки подписанных пакетов `node scripts/booking-select.mjs select <хранилище> <открытый-ключ> <версия>` проверяет совместимость, подпись и файлы и атомарно записывает текущую и предыдущую выбранную версию. `node scripts/booking-select.mjs rollback <хранилище> <открытый-ключ>` вручную выбирает предыдущую проверенную версию. Команды не изменяют БД и не перезапускают службу. Для загрузки выбранной версии задайте `NOVA_BOOKING_USE_SELECTION=true`, `NOVA_BOOKING_PACKAGE_STORE` и `NOVA_BOOKING_TRUSTED_KEY`; `NOVA_BOOKING_PACKAGE_VERSION` при этом не задаётся. После изменения выбора требуется контролируемый перезапуск API.

Поддерживаются только пакеты с версией схемы 1. Это не автоматический откат в случае ошибки запуска: оператор должен проверить состояние и самостоятельно восстановить предыдущий выбор; откат миграций базы не реализован. Одинаковый номер схемы не заменяет проверку совместимости данных и резервное копирование. Тесты используют два фиктивных номера с одинаковым кодом; переход между настоящими релизами не проверен. Интерфейс по-прежнему входит в сборку NOVA.
